From raw race data to controlled records

The story behind Project F1REBALL.

The original project motivation was simple: Formula 1 produces fast-changing, high-volume data that becomes difficult to trust when it lives in spreadsheets or disconnected files. Project F1REBALL organizes that information into a database where records can be validated, queried, updated, and reviewed consistently.

Class assignment alignment

E/R design, relational schema, normalization, SQL testing, stored routines, trigger-based failure handling, and indexing analysis.

Data Origin

The dataset combines Formula 1 race schedule data with session-level and event-level data covering drivers, meetings, telemetry, weather, pit stops, stint strategy, and race control messages.

1950-2024 schedule history represented

Data Area Purpose Example Quality Concern
Telemetry Speed, RPM, throttle, brake, gear, and DRS measurements. Impossible speeds, missing driver/session keys, duplicate timestamps.
Weather Track and air conditions that affect tyre and race strategy. Out-of-range temperatures, null rainfall, inconsistent timestamps.
Race Control Flags, incident messages, scopes, sectors, laps, and affected drivers. Messages without valid session context or invalid flag values.
Pit and Stints Operational events for pit stops, tyre compounds, and lap ranges. Negative lap ranges, unusual pit durations, unsupported compounds.

Transformation Journey

Phase one began with the problem statement and E/R design. Phase two moved the project into SQL implementation, query testing, failure handling, and performance review.

  1. Define the data collection need

    Identify users such as teams, officials, broadcasters, and analysts, then determine what each user needs to collect and review.

  2. Model entities and relationships

    Create an E/R model linking drivers, meetings, sessions, race schedules, telemetry, weather, pit stops, stints, and race control events.

  3. Normalize the structure

    Remove transitive dependencies by separating country and circuit lookup data from meetings and sessions, supporting BCNF/3NF reasoning.

  4. Load and validate records

    Convert CSV files into database tables, check key relationships, standardize datatypes, and preserve nullable fields where the source legitimately lacks information.

  5. Query, review, and improve

    Use joins, grouping, ordering, subqueries, stored functions, triggers, and indexes to support repeatable reporting and operational review.

Assumptions and Controls

Assumptions

Each session belongs to one meeting. Telemetry and weather timestamps are event observations. Some race control messages may not involve a specific driver, lap, or sector.

Validation Steps

Review row counts after loading, inspect missing keys, check permitted categories, compare date ranges, and use report queries to identify records needing follow-up.
